# mai22maitouch_sync 使用说明

maimai基板（RingEdge2）与maimaiでらっくす外设的串口桥接与转发工具。程序运行在 PC 上，作为**游戏主机**与**触摸控制器 / 灯光板 / 摄像机 / aime 读卡器**等外设之间的中介，实现触摸数据格式转换、外设透明转发、读卡器兼容处理等功能。

所有串口与功能开关都通过同目录下的 `m22mt_config.ini` 配置，**改配置无需改代码**。

本repo重度依赖QWen3.8-Max，内容大部分由AI生成，人工核查亦有疏忽，如有错漏还请自行更正。

> ⚠️ mai22maitouch_sync并不包含关于按键IO的模拟与转译，我目前使用837-15257-91原生的JVS-485接口实现对RingEdge的兼容，除此之外，对于灯光相关功能，837-15067-02在大多数情况下是必须的，对于摄像机相关功能，只能使用官方的摄像机模组（XKT-1999）并将其网络接口连接在RingEdge相同子网内。

## 一、功能总览

| 模块 | 作用 | 相关端口 |
|---|---|---|
| **触摸桥接** | mai2 格式(9字节)触摸数据 → mai 格式(14字节)，1P/2P 合并，垂直同步定频发送，可调输入延迟 | `GOPI` / `CIPO_1P` / `CIPO_2P` |
| **外设转发** | 灯光、摄像机双向透明转发（可选空闲分帧，解决逐字节打散） | `Light_IN/OUT`、`Camera_IN/OUT` |
| **读卡器转发** | aime 读卡器透传，并提供两种 2P 兼容处理 | `CARD_IN` / `CARD_OUT` |
| **端口日志** | 每端口收发字节落盘，便于抓包分析 | 全部端口 |
| **丢包率统计** | 周期性统计触摸发送丢包率，仅异常时打印 | `GOPI` |
| **命令控制** | `{STAT}` 激活 / `{HALT}` 停止 / `{XXkY}` 注册映射 / `{XXth}` 查询映射 | `GOPI` |

## 二、快速开始

### 运行方式

```powershell
# 方式一：源码运行（需 Python 3.x + pyserial）
python mai22maitouch_sync.py

# 方式二：Release中下载打包好的 exe
mai22maitouch_sync.exe
```

### 首次运行

- 若同目录下**没有** `m22mt_config.ini`，程序会自动生成一份包含全部 section 与注释的默认配置，然后退出提示。
- 按你的实际硬件（端口号、波特率）修改 `m22mt_config.ini` 后重新运行即可。

### 依赖

`pyserial`

## 三、配置文件详解（重点）

配置文件：`m22mt_config.ini`（与程序/exe 同目录，`configparser` 格式）。

### 3.1 加载规则

| 情况 | 行为 |
|---|---|
| 文件不存在 | 生成内置默认配置并提示，本次不运行 |
| 文件损坏/读取失败 | 回退内置默认配置继续运行 |
| 某 section 缺失 | 该端口用内置默认值 |
| 某键缺失 | 该键回退内置默认值（**升级新增的键无需手动补旧配置**） |

> ⚠️ **注释必须整行**（以 `;` 开头）。`configparser` 不支持行内注释，若写成 `port = COM3 ; 游戏口`，`;` 后的内容会被当作端口值的一部分，导致端口打开失败。

### 3.2 全局参数 `[global]`

| 键 | 默认 | 含义 |
|---|---|---|
| `delay_ms` | `16` | 触摸输入延迟(ms)。数据进入延迟队列后延后发送，用于对齐节拍。范围建议 0–100 |
| `vsync_rate` | `60` | 垂直同步发送频率(Hz)。触摸状态回传游戏的固定节拍。受波特率带宽限制（见下方提示） |
| `idle_ms` | `4` | **默认**空闲分帧阈值(ms)。端口未单独设 `idle_ms` 时用它 |
| `loss_period` | `10` | 丢包率统计周期(秒)。每周期结束仅在丢包率>0 时打印一行 |

> 💡 带宽提示：`9600` 波特下 14 字节触摸包（8N1=10bit/字节）理论上限约 `9600/(14×10)≈68.5` 包/秒，`vsync_rate=60` 已占约 87.5% 带宽。若 `vsync_rate` 超过该上限，程序启动时会告警且无法稳定达标。

### 3.3 端口通用键

每个端口 section 都含以下键：

| 键 | 含义 |
|---|---|
| `port` | 串口号（如 `COM34`）。**留空则停用该端口 / 该组转发** |
| `baud` | 波特率 |
| `framing` | 空闲分帧开关。**仅对转发口(`Light`/`Camera`/`CARD`)生效**；触摸口(`GOPI`/`CIPO`)忽略此项。`1`=按空闲分帧整条转发，`0`=即时透传 |
| `log` | `1`=记录该端口收发到 `logs/<name>.log`，`0`=不记录 |
| `idle_ms` | 该端口的空闲分帧阈值(ms)，超过此空闲即认为一帧结束。仅 `framing=1` 时有意义 |

布尔类键（`framing`/`log`/`dummy_2p`/`hinata`）识别：`1/true/yes/on` 为真，`0/false/no/off/空` 为假。

### 3.4 端口清单与接线

命名约定：**`X_IN` = 外设→PC 侧（接外设板）**，**`X_OUT` = PC→游戏侧（接游戏）**。程序在两侧之间做转发/处理。

| Section | 侧 | 物理连接到 | 默认端口 | 默认波特率 |
|---|---|---|---|---|
| `GOPI` | 游戏侧 | 游戏主机（触摸/命令口） | `COM34` | `9600` |
| `CIPO_1P` | 外设侧 | 1P 触摸控制器 | `COM3` | `9600` |
| `CIPO_2P` | 外设侧 | 2P 触摸控制器（**留空则禁用 2P**） | *(空)* | `9600` |
| `Light_IN` | 外设侧 | 灯光控制板 | `COM21` | `115200` |
| `Light_OUT` | 游戏侧 | 游戏灯光输出 | `COM31` | `115200` |
| `Camera_IN` | 外设侧 | 摄像机控制板 | `COM32` | `115200` |
| `Camera_OUT` | 游戏侧 | 游戏摄像机输出 | `COM33` | `115200` |
| `CARD_IN` | 外设侧 | aime 读卡器 | `COM35` | `38400` |
| `CARD_OUT` | 游戏侧 | 游戏读卡器侧 | `COM36` | `38400` |

> 上表为程序生成默认配置时写入的值，**实际请以你的硬件和 `m22mt_config.ini` 为准**（波特率尤其要按外设实际规格填写）。

**转发配对**（双向透明）：`Light_IN ↔ Light_OUT`、`Camera_IN ↔ Camera_OUT`、`CARD_IN ↔ CARD_OUT`。任一口 `port` 留空，则整组停用。

### 3.5 `[CARD_OUT]` 专用开关

除通用键外，`[CARD_OUT]` 还有两个读卡器兼容开关（默认都 `0`，一般二选一）：

#### `dummy_2p` —— 软件模拟 2P 读卡器（游戏侧拦截）

- **用途**：只接了 **1P 原版读卡器**、但游戏自检要求 1P+2P 两台读卡器都应答时，用软件顶替 2P 通过自检。
- **行为**（在 `CARD_OUT` 收到游戏发往 `addr=0x01`(2P) 的指令时拦截）：
  - `0x62` 切普通模式：首次回 `status=00`，其后回 `03`（与真实读卡器一致）
  - `0x30` 查固件版本：回 `TN32MSEC003S F/W Ver1.0`
  - `0x32` 查硬件版本：回 `TN32MSEC003S H/W Ver3.0`
  - `0x54`/`0x50` 设 KeyB/KeyA：回 `status=00`
  - `0x40` 轮询等其余 2P 指令：忽略（不应答、不转发）
  - 非 2P 帧（1P、灯光板等）：正常转发给读卡器
- **仅在 `framing=1` 分帧下生效**（不分帧无法可靠解析帧边界）。

#### `hinata` —— Hinata 兼容读卡器模式（读卡器侧拦截）

- **用途**：接的是 **Hinata TN32 兼容读卡器**（单台设备同时应答 1P`addr=0x00` 与 2P`addr=0x01`）。读卡时它会把**同一张卡同时上报给 1P 和 2P**，导致 2P 也触发登录、卡在登录确认。
- **行为**（在 `CARD_IN` 收到读卡器应答、转发给游戏前拦截）：
  - `addr=0x01`(2P) 且 `cmd=0x42`(卡片检测) 且**有卡**(数据长度>1) 的应答 → **改写为"无卡"**（`status=00, 数据长度=01, data=00`，**保留原包序号**）
  - 其余帧一律原样透传：**1P 卡片正常上报**、2P 无卡、2P 预热(`st=02`)、其它命令都不受影响
- **仅在 `framing=1` 分帧下生效**。

#### 两者区别与选择

| | `dummy_2p` | `hinata` |
|---|---|---|
| 硬件场景 | 只接 **1P 原版**读卡器 | 接 **Hinata 兼容**读卡器（单台双地址） |
| 拦截侧 | 游戏侧（`CARD_OUT` 收命令） | 读卡器侧（`CARD_IN` 收应答） |
| 解决问题 | 2P 缺失导致**自检不通过** | 2P 误报卡片导致**卡在登录** |
| 处理指令 | 2P 自检指令(`0x62/0x30/0x32/0x54/0x50`) | 2P 卡片检测(`0x42`) |

> 用 Hinata 读卡器时通常 `dummy_2p=0`、`hinata=1`（Hinata 天然能过自检，无需软件模拟）；只接 1P 原版读卡器时 `dummy_2p=1`、`hinata=0`。

## 四、功能模块详解

### 4.1 触摸桥接（`GOPI` / `CIPO_1P` / `CIPO_2P`）

**数据流：**

```
游戏主机 ──命令{STAT}/{HALT}/{XXkY}/{XXth}──▶ GOPI ──转发命令──▶ CIPO_1P / CIPO_2P
                                                    ▲
触摸控制器 ──mai2触摸数据(9字节)──▶ CIPO_1P/2P ──变换+合并+定频──┘ 回传 mai格式(14字节) 到 GOPI ──▶ 游戏
```

- **格式变换**：触摸控制器发来 mai2 格式（9 字节，`0x28`…`0x29`），程序按区位映射转换为 mai 格式（14 字节）。1P 映射到字节 1–4，2P 映射到字节 7–10；启用 2P 时把 2P 结果合并进 1P 帧。
- **垂直同步发送**：收到 `{STAT}` 激活后，按 `vsync_rate` 定频把最新触摸状态回传游戏；采用绝对时间栅格推进，卡顿后重新对齐、不爆发式补发。
- **输入延迟**：`delay_ms` 让触摸数据延后进入发送队列。
- **命令**（游戏经 `GOPI` 下发）：
  - `{STAT}`：激活桥接，回全零状态并向触摸控制器转发 `{STAT}`
  - `{HALT}`：停止桥接，向触摸控制器转发 `{HALT}`
  - `{XXkY}`：注册按键映射（`XX`→`Y`），回应 `(XX  )`
  - `{XXth}`：查询映射，回应 `(XX Y)`
- **2P 启用**：`CIPO_2P` 的 `port` 非空即启用 2P；若该口打开失败，自动降级为仅 1P 继续运行。

### 4.2 外设转发（`Light` / `Camera`）

- 每组两个串口双向透明转发，**不改写任何字节**。
- `framing=1`（默认）：累积字节，超过 `idle_ms` 空闲即认为一帧结束，**整帧一次性写出**，使字节在 UART 上连续发出（等效直接跳线），解决逐字节交付导致的"一字一停"。
- `framing=0`：收到即转发（即时透传）。
- 任一口 `port` 留空或被占用，则跳过该组（不影响其它组）。

### 4.3 读卡器转发（`CARD`）

- `CARD_IN`(接读卡器) ↔ `CARD_OUT`(接游戏) 双向转发，同样支持空闲分帧。
- 在游戏侧路径按 `dummy_2p` 拦截 2P 自检；在读卡器侧路径按 `hinata` 改写 2P 读卡应答（详见 3.5）。
- aime 协议帧结构、校验和、转义规则等细节见 `aime/aime指令分析.md`；Hinata 读卡器特性见 `aime/hinata_tn32模式应答分析.md`。

## 五、典型配置场景（配方）

### 场景 A：单人 1P 触摸（最简）

```ini
[GOPI]
port = COM34        ; 接游戏主机
[CIPO_1P]
port = COM3         ; 接 1P 触摸控制器
[CIPO_2P]
port =              ; 留空 → 禁用 2P
```

### 场景 B：双人 1P + 2P 触摸

```ini
[CIPO_1P]
port = COM3
[CIPO_2P]
port = COM4         ; 非空即启用 2P
```

### 场景 C：只接 1P 原版读卡器（软件顶替 2P 过自检）

```ini
[CARD_IN]
port = COM35        ; 接真实 1P 读卡器
[CARD_OUT]
port = COM36        ; 接游戏
framing = 1         ; 必须分帧，dummy_2p 才生效
dummy_2p = 1        ; 软件模拟 2P 自检应答
hinata = 0
```

### 场景 D：接 Hinata 兼容读卡器（避免 2P 卡登录）

```ini
[CARD_IN]
port = COM35        ; 接 Hinata 读卡器
[CARD_OUT]
port = COM36        ; 接游戏
framing = 1         ; 必须分帧，hinata 才生效
dummy_2p = 0
hinata = 1          ; 拦截 2P 读卡应答为无卡
```

### 场景 E：不需要某外设

把对应组的两个 `port` 任一**留空**即可停用该组转发（如不用摄像机，`[Camera_IN] port =` 留空）。

## 六、端口日志

- `log = 1` 的端口，收发字节写入 `logs/<name>.log`。
- 每行格式：`[时间] RX/TX <hex> | <ascii>`（收发合并到同一文件，`RX`=本端收到，`TX`=本端发出）。
- 每次启动写入一行会话头：`===== 会话开始 <时间> ===== port=<端口> baud=<波特率>`。
- 抓包分析时注意**方向约定**：日志站在"本端口"视角，不同端口/不同抓包点的 RX/TX 含义可能相反。

---

## 七、丢包率统计

- 每 `loss_period` 秒统计上一周期触摸发送丢包率：`期望 ≈ 活跃时间 × vsync_rate`，与实际发送数比较。
- 仅当丢包率 > 0（且缺口 > 1 个包，容忍启动/周期边界抖动）时打印一行：
  `[发送频率] 近10s 丢包率 X%（期望≈N，实际M）`
- 无丢包时不输出，避免刷屏。

## 八、常见问题（FAQ）

| 现象 | 原因 / 处理 |
|---|---|
| `[串口占用] ... 已被其他程序占用` | 该 COM 口被其它程序（或另一个本程序实例）占用，关闭占用者或换口 |
| `[串口错误] ... 端口不存在` | 端口号写错或设备未连接，检查设备管理器里的实际 COM 号 |
| 端口配置了却打不开、值很奇怪 | 多半是**行内注释**导致，注释必须整行以 `;` 开头 |
| 触摸无反应 | 确认已收到 `{STAT}` 激活；检查 `GOPI`/`CIPO` 端口与波特率 |
| 触摸发送丢包告警 | `vsync_rate` 可能超过波特率带宽上限，降低 `vsync_rate` 或提高 `GOPI` 波特率 |
| 游戏自检卡在 2P 读卡器 | 只接 1P 原版读卡器时设 `dummy_2p = 1`（见场景 C） |
| 2P 刷卡后卡在登录确认 | 用 Hinata 兼容读卡器时设 `hinata = 1`（见场景 D） |
| `dummy_2p`/`hinata` 不生效 | 二者都要求 `[CARD_OUT]`/`[CARD_IN]` 的 `framing = 1` |
| 外设（灯光/摄像机）数据断续 | 保持 `framing = 1`，必要时调整该口 `idle_ms` |
